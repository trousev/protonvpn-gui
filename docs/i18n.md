# Localization

The application speaks English and Russian, and adding a third language is adding a directory. The
catalogue is [Project Fluent](https://projectfluent.org/), the format Firefox uses, and the reason
is one requirement above the others: **a translator has to know where the string appears**, and
Fluent puts that comment in the same file, on the line above the message.

```
crates/protonvpn-core/i18n/
    en/          ← the source language; every other locale is measured against it
        chrome.ftl
        status.ftl
        …
    ru/
        chrome.ftl
        status.ftl
        …
```

`crates/protonvpn-core/build.rs` reads all of it **before the crate compiles**, generates the
`Locale` enum and one typed method per message, and refuses to build the workspace at all if a
locale is incomplete. `crates/protonvpn-core/src/i18n.rs` is the runtime half: the bundles, the
fallback, and the handful of helpers (`connection_label`, `age_text`, …) that are a `match` over an
enum rather than a sentence.

## The rules the build enforces

Every one of these fails `cargo build`, and therefore `cargo test`, `cargo clippy` and CI:

| Rule | Why |
|---|---|
| Every locale carries the same `.ftl` files as `en` | a gap should be a missing file, not a message nobody noticed |
| Every locale carries the same message ids as `en` | an untranslated string is a build error, never a silent fallback |
| Every message has a `#` comment | the comment is the translator's only view of the screen |
| Every locale uses the same `$variables` as `en` | a translation that drops `{$port}` drops the port |
| A `$variable` is a number in every locale, or a string in every | `[few]` only matches a number, and Russian needs `[few]` |
| An id starts with its file's name (`settings-…` in `settings.ftl`) | an id says where to look |
| No terms, no attributes, no message-to-message references | one message is one string on one screen |
| The only function is `NUMBER()` | any other formatter would not be installed |
| Every message is called from somewhere in the workspace | a string nobody asks for is translated forever for nothing |

The last one is worth repeating: **delete a message when its last call site goes.** A catalogue that
only grows is a catalogue nobody trusts.

A gap is reported where it is, once:

```
error: i18n/ru: `status-target-random` is untranslated
error: i18n/ru/status.ftl: syntax error at byte 1230: "status-age-seconds = обновлено { $секунд } ..."
```

A file that does not parse is not also sixty "untranslated" lines — the syntax error is the whole
story until it is fixed. `./scripts/translate --check` prints the same list without calling a model,
which is what CI runs.

## Adding a string

1. Write the English message in the right file under `i18n/en/`, with a `#` comment saying where it
   appears, how much room it has, and anything a translator could not guess:

   ```ftl
   # The Connect button on the Overview page. Short: it sits in a row beside the status chip, and
   # the selected connection's name is shown separately underneath.
   # $target is a country, a city or a server name as the CLI spells it — never translate it.
   overview-connect = Connect to { $target }
   ```

2. Add the same id to `i18n/ru/`, with the same comment and the same `$variables`.
3. Call it: `app.i18n.overview_connect(app.selected_name())`. The method is generated, takes exactly
   the variables the message uses, and appears in completion.

Run `./scripts/translate` and it will do steps 1–3's translation half for you.

## Writing the context comment

The comment is not a summary of the string — it is the answer to "where is this, and what could go
wrong". Say which screen, which control, and what the space is like. Two examples, both real:

```ftl
# The collapsed console bar while a command runs. $command is the argv, verbatim — the exact
# program and flags that were executed — and is never translated.
status-runner-running = working: { $command }
```

```ftl
# What a connect is aimed at on a Secure Core route. Proton's own product name — leave it as it is.
status-target-secure-core = Secure Core
```

## Adding a language

```sh
mkdir crates/protonvpn-core/i18n/de
# copy the English files, translate them, keep the comments
./scripts/translate
```

`Locale` gains a `De` variant, the language picker gains an entry, and the build starts failing
until every message is there. `$LANG=de_DE.UTF-8` then selects it without any further change.

## Plurals

English plurals are not a pattern to copy. Fluent selects on the CLDR category of a number, and
Russian has three forms where English has two:

```ftl
status-age-minutes = { $minutes ->
        [one] обновлено { $minutes } минуту назад
        [few] обновлено { $minutes } минуты назад
        [many] обновлено { $minutes } минут назад
       *[other] обновлено { $minutes } минут назад
    }
```

A number reaches the selection only through `NUMBER($n)` (or as the selector itself). `{ $n }` as a
plain placeable is a *string*, `[few]` will never match it, and `build.rs` will say so.

## The desktop entry

`Name`, `GenericName` and `Comment` in a `.desktop` file are read by the desktop, not by the running
process, so the spec localizes them by suffixing the key — `Name[ru]=…` — and every language is
written at once. `desktop::identity_keys` does that from the catalogue, and a test keeps the
generated entry identical to `packaging/protonvpn-gui.desktop`. Adding a language therefore means
adding its three lines to that file too; the test says so the moment you forget.

## What is not translated

Data. A server name, a country the CLI printed, a city, an exit code, a command line, a URL, a
path, a version. Those are facts about the outside world, and the console exists to show them
exactly as they arrived. The line between the two is the line between *our words* and *the CLI's
words*, and it is the whole reason the console is trustworthy.

## Translation

`./scripts/translate` fills every gap — a missing message, a missing variable, a whole missing
file — using an LLM, and refuses to write anything that does not survive the same checks
`build.rs` applies. It reads `$OPENAI_API_KEY`, uses `gpt5-terra` unless `$TRANSLATE_MODEL` says
otherwise, and is expected to be run **before opening a pull request**; see
[`AGENTS.md`](../AGENTS.md).
